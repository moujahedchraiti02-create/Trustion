==================================================
OBJECTIVE
==================================================

Introduce explicit cryptographic CHAIN EPOCHS and immutable MERKLE ANCHORS so TRUSTION can establish bounded, independently verifiable evidence periods without rewriting historical ledger evidence.

An epoch is an explicitly identified contiguous set of ledger entries governed by one declared hash-chain algorithm/version.

Closing an epoch creates a deterministic Merkle root over its immutable ledger evidence and records an auditable anchor.

This establishes the foundation for later:
- audit-period sealing
- voyage/reporting-period anchoring
- offline evidence packages
- external/notarial anchoring
- DNV/class/regulatory verification workflows

Do NOT claim external blockchain, TSA, DNV certification, class approval, or regulatory approval.
This task builds the internal cryptographic foundation only.

==================================================
1. DATA MODEL
==================================================

Create a chain_epochs table with at least:

id
epochId                stable UUID or equivalent unique identifier
vesselId               FK to vessel
algorithm              e.g. "SHA-256"
canonicalizationVersion
status                 OPEN | CLOSED
startEntryId
endEntryId              nullable while OPEN
entryCount
merkleRoot              nullable while OPEN
previousEpochRoot        nullable for first trusted epoch
openedAt
closedAt                 nullable while OPEN
createdAt

Add appropriate uniqueness/index constraints.

There must never be more than ONE OPEN epoch per vessel.

Enforce this at DB level with an appropriate partial unique index where supported.

Create append-only chain_epoch_events with at least:

id
epochId
eventType               EPOCH_OPENED | EPOCH_CLOSED
eventTimestamp
metadata
createdAt

Epoch event history must never be silently rewritten.

Do not place private key material in either table.

==================================================
2. TRUST BOUNDARY / LEGACY HISTORY
==================================================

Do NOT automatically absorb legacy entries 1–19 into a SHA-256 epoch.

The system must support establishing a new trusted SHA-256 epoch boundary without modifying those records.

If existing valid SHA-256 entries can be safely included based on deterministic verification, they may be included.

Never classify an entry as SHA-256-valid merely because its stored hash length is 64 characters.

Actual recomputation/verification is required.

If a safe automatic boundary cannot be established, fail explicitly rather than guessing.

Legacy history should remain visible to auditors as legacy/unanchored evidence.

==================================================
3. EPOCH OPENING
==================================================

Implement an ADMIN-controlled operation to open an epoch for a vessel.

Example API shape:

POST /api/chain-epochs/open

Input:
{
  "vesselId": <id>,
  "algorithm": "SHA-256",
  "canonicalizationVersion": "v1"
}

Requirements:

- ADMIN authorization
- reject if vessel already has OPEN epoch
- record deterministic start boundary
- append EPOCH_OPENED event
- transactional DB operation
- no mutation of existing ledger entries
- return epoch identity and boundary metadata

Do not accept arbitrary Merkle roots or hashes from the client.

==================================================
4. ASSIGNING NEW EVIDENCE TO AN EPOCH
==================================================

Add nullable epochId / chainEpochId to ledger_entries.

For all NEW SHA-256 ledger entries after a vessel has an OPEN epoch:

- server determines the OPEN epoch
- ledger entry is assigned to that epoch
- caller cannot choose or override epochId
- hashing/signing behavior from previous tasks remains intact

OPERATOR and EDGE_INGEST must follow the same epoch assignment rule.

Existing rows remain untouched unless assignment can be done without modifying immutable historical evidence.

Prefer no historical ledger mutation.

==================================================
5. EPOCH CLOSURE
==================================================

Implement:

POST /api/chain-epochs/:epochId/close

ADMIN only.

Closure must execute transactionally.

Before closure:

1. Load all ledger entries assigned to the epoch in deterministic order.
2. Require at least one entry.
3. Recompute and verify every entry's SHA-256 rawHash.
4. Verify chain linkage inside the epoch.
5. Fail CLOSED operation if any assigned evidence fails verification.
6. Determine endEntryId and entryCount from DB — never from client input.

Then build a deterministic Merkle tree.

==================================================
6. MERKLE LEAF DEFINITION
==================================================

Do NOT invent a second evidence representation.

Use the immutable cryptographic identity already stored for each ledger entry.

Preferred leaf:

leaf[i] = ledger_entries.chainHash

Before use, validate that each leaf is a valid 64-character SHA-256 hex value.

Merkle tree requirements:

- SHA-256
- deterministic ordering by ledger entry ID ascending
- pair adjacent nodes
- if a level contains an odd node count, duplicate the final node
- parent = SHA256(left || right)

Use one representation consistently.

If the existing buildMerkleProof/helper already defines compatible semantics, REUSE it rather than implementing a competing algorithm.

If existing semantics differ, preserve backward compatibility and document the chosen epoch algorithm/version explicitly.

==================================================
7. MERKLE ROOT + EPOCH ANCHOR
==================================================

On successful closure store:

endEntryId
entryCount
merkleRoot
closedAt
status = CLOSED

Append EPOCH_CLOSED to chain_epoch_events.

The closing transaction must be atomic:
either the epoch closure + root + event all commit,
or none commit.

A CLOSED epoch is immutable.

Do not allow:
- reopening
- changing root
- changing boundaries
- adding later evidence to it

==================================================
8. EPOCH-TO-EPOCH LINKING
==================================================

When opening epoch N+1 for a vessel:

previousEpochRoot should reference the immediately preceding CLOSED trusted epoch's merkleRoot when one exists.

This creates:

Epoch N evidence
      ↓
Merkle Root N
      ↓
previousEpochRoot in Epoch N+1

Do not use the legacy MD5 chain as a trusted previous root.

First trusted SHA-256 epoch may have:

previousEpochRoot = null

That is valid and explicitly represents the cryptographic trust boundary.
