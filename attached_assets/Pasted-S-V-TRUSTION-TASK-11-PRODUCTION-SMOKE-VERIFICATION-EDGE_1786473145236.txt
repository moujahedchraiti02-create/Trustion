ARCHITECTURAL CONTEXT

S³V TRUSTION is the first application layer of the broader TRUSTION architecture.

This application layer is focused on maritime carbon evidence, regulatory compliance, auditability, and technically defensible evidence under applicable maritime/international regulatory frameworks.

The current server signature proves that TRUSTION received and committed evidence.

It does NOT by itself prove that a specific vessel/device produced the original measurement.

Task #11 must close that provenance gap.

==================================================
PHASE B — EDGE DEVICE IDENTITY
==================================================

Implement a real device identity registry.

Each Edge device must have at minimum:

- deviceId
- vesselId and/or vessel IMO binding using the existing vessel model
- keyId
- Ed25519 publicKey
- status:
  ACTIVE
  RETIRED
  REVOKED
- activatedAt
- retiredAt nullable
- revokedAt nullable
- revocationReason nullable
- createdAt

Security invariants:

1. A device identity is bound to exactly the vessel it is authorized to submit evidence for.
2. An EDGE_INGEST caller must NOT be able to submit evidence for arbitrary vessels.
3. Private device keys must NEVER be stored by the central TRUSTION server.
4. Private device keys must NEVER be accepted through a public API.
5. keyId must be deterministically derived from the device public key.
6. Revoked devices cannot submit new evidence.
7. Historical evidence from a subsequently revoked device remains preserved and cryptographically verifiable with proper revocation context.

Do not implement TPM/HSM hardware integration yet.
Design the model so TPM/HSM-backed keys can replace software-held Edge keys later without changing the evidence format.

==================================================
PHASE C — SOURCE-SIGNED EDGE EVIDENCE
==================================================

Implement source signing.

The Edge/device side must sign the canonical evidence payload BEFORE it reaches the central TRUSTION server.

Required ingest fields should include, using existing names where possible:

- deviceId
- vessel identity
- measurement/event payload
- device timestamp
- sequence number if not already available
- device keyId
- device signature

Define ONE deterministic canonical serialization format.

The signature must cover all security-critical provenance fields required to prevent substitution between:
- devices,
- vessels,
- measurements,
- timestamps,
- and sequence positions.

The server must:

1. authenticate the EDGE_INGEST request;
2. resolve deviceId from the device registry;
3. enforce vessel binding;
4. resolve the registered device public key;
5. verify the device signature BEFORE ledger insertion;
6. reject invalid signatures;
7. reject unknown devices;
8. reject revoked devices for new submissions;
9. reject vessel/device mismatch;
10. preserve device provenance with the ledger entry.

IMPORTANT:
Do not trust a publicKey supplied in the evidence request.
The authoritative device public key must come from the server-side device registry.

==================================================
PHASE D — DUAL SIGNATURE / PROVENANCE MODEL
==================================================

Do NOT remove the existing TRUSTION server signing mechanism.

We now need two distinct cryptographic assertions:

A. SOURCE SIGNATURE
“This registered Edge device signed this measurement.”

B. TRUSTION RECEIPT/LEDGER SIGNATURE
“The TRUSTION server accepted and committed this evidence.”

Store enough information to distinguish them unambiguously.

For each new Edge-originated ledger entry, preserve at minimum:

- sourceDeviceId
- sourceKeyId
- sourceSignature
- sourceSigningMode
- server keyId
- server signature
- existing hash-chain fields

Do not label the server signature as proof of sensor origin.

Human OPERATOR submissions must remain distinguishable from Edge-device submissions.

Never silently represent OPERATOR-entered evidence as device-signed evidence.

==================================================
PHASE E — REPLAY / SEQUENCE DEFENSE
==================================================

Implement the minimum defensible anti-replay mechanism.

For each device maintain monotonic sequence semantics.

Reject:
- duplicate sequence numbers;
- obvious replay of already accepted signed evidence;
- sequence regressions unless an explicitly modeled recovery/backfill rule allows them.

Do not invent a complex offline synchronization protocol in this task.

If offline/backfill requires a later dedicated design, preserve the schema needed for it and document the limitation accurately.

Concurrency matters:
ensure two simultaneous submissions cannot both incorrectly pass sequence validation.
